# Decode

## Prerequisites
- [[Transformer]]
- [[Prefill]]
- [[KV Cache]]

摘要：Decode 是 LLM推論的生成階段，屬於Memory-bound，逐字生成Token。



## 虛擬團隊補充說明：Decode 階段的硬體挑戰

> **教育員白話文解釋**：想像你正在寫作，每寫下一個字，你都需要回顧之前寫過的所有字，並思考下一個最合理的字是什麼。這就是 Decode 階段在做的事情。因為你必須等前一個字確定了，才能想下一個字，所以這個過程無法「多人同時分工」（無法大規模平行運算）。

**為什麼 Decode 是 Memory-bound (受限於記憶體頻寬)？**

在 Decode 階段，雖然每次運算（推論出一個 Token）所需的計算量很少，但硬體卻必須將龐大的模型權重參數和過去累積的 **KV Cache** 從主記憶體（例如 HBM 或 GDDR）搬運到運算單元（例如 GPU 的 SRAM 或是 TPU 的 Matrix Multiply Unit）。

由於計算速度極快，但資料搬運的速度相對緩慢，導致運算單元大部分的時間都在「等待資料送達」。這就像是有一個超級快的主廚（運算單元），但他只能依賴一個走得很慢的服務生（記憶體頻寬）來送食材，主廚的產能完全被服務生的速度限制住了。

因此，提升 Decode 效能的關鍵在於**提升記憶體頻寬**（讓服務生走快一點）或是**減少需要搬運的資料量**（例如 KV Cache 量化）。

## 已知事實
Decode（解碼）是大型語言模型推論過程中的第二個階段。在處理完使用者的提示詞後，模型會進入逐字生成回應的過程。因為生成下一個字必須依賴上一個字的結果，所以這個階段無法進行大規模平行運算，高度依賴記憶體頻寬（Memory-bound）。

## 原理
Decode 階段的本質是一個自迴歸（Auto-regressive）過程：模型根據輸入和前面已經生成的詞，預測出下一個最可能的詞。為了避免每次生成新詞時都要重新計算之前所有的詞，系統會將之前計算過的中間狀態儲存起來，這就是所謂的 [[KV Cache]]。

## 限制
每次生成一個新詞，運算單元只需要做很少量的計算，但卻需要從主記憶體中把龐大的模型參數和整套 KV Cache 讀取出來。這導致運算單元常常在「等待」資料傳輸，算力利用率極低。因此，Decode 階段被稱為 Memory-bound（受限於記憶體頻寬）任務。

## 未知問題
如何突破這道記憶體牆，進一步提升記憶體頻寬與容量，同時降低延遲與功耗，是未來的研究重點。

## 最佳實務
透過軟體層面的技術更有效地管理記憶體碎片，或是將 KV Cache 進行低精度量化，以減少記憶體佔用與傳輸量。

## 個人見解
Decode 階段的效能瓶頸是目前 LLM 推論面臨的最大挑戰，解決 Memory-bound 問題對於提升系統吞吐量至關重要。

## 方案與觀點分析

### 方案一：採用超高頻寬記憶體技術
在硬體設計上採用提供極高資料吞吐量的記憶體技術，加速參數與 KV Cache 的讀取。
- 優點：直接暴力解決記憶體頻寬不足的問題，無須更動軟體架構。
- 缺點：記憶體容量有限，且單價極高，封裝良率挑戰大。
- 成本：硬體採購與製造成本極高。
- 維護性：硬體升級依賴半導體製程與封裝技術，迭代不易。
- 風險：供應鏈產能若受限，會嚴重影響硬體出貨。

### 方案二：KV Cache 量化與管理優化
在軟體層面，透過技術更有效地管理記憶體碎片，或是將 KV Cache 進行低精度量化（如從 FP16 降至 [[INT8]]），以減少記憶體佔用與傳輸量。
- 優點：不需要新硬體，即可顯著提升同時服務的使用者數量（Batch Size），進而提升吞吐量。
- 缺點：量化可能造成模型生成品質的微幅下降（精度損失）。
- 成本：極低的硬體成本，主要的成本在於軟體研發。
- 維護性：軟體方案易於部署與更新。
- 風險：如果演算法不能妥善處理極端值，可能導致模型產生幻覺或亂碼。

### 方案三：記憶體內運算架構
改變傳統架構，將運算單元直接整合進記憶體晶片內部，讓資料「就地運算」，大幅減少資料在匯流排上的搬運。
- 優點：從根本上消除記憶體牆，極大降低資料傳輸功耗，非常適合 Decode 這類運算。
- 缺點：生態系尚未成熟，無法直接支援現有的複雜編譯器與模型架構。
- 成本：需重新開發專用硬體與軟體生態，初期投入巨大。
- 維護性：因缺乏通用標準，軟硬體維護與升級非常困難。
- 風險：若技術無法成為主流標準，可能面臨被市場淘汰的風險。
