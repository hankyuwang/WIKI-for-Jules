# 算子融合 (Operator Fusion)

摘要：算子融合是 AI 編譯器將多個神經網路層 (Operations) 合併執行的技術，旨在減少 Kernel Launch 開銷與記憶體存取次數，是突破「記憶體牆」的關鍵軟體優化技術。

## Prerequisites
- [[AI硬體之記憶體牆問題]]
- [[深度學習運算原理]]

### 白話文解釋 (五分鐘版)
想像你在廚房做菜（執行神經網路），算子（Operator）就是不同的料理步驟，比如：切菜（算子A）、炒菜（算子B）、裝盤（算子C）。
- **沒有融合的情況下**：你切完一片菜，把它放進大冰箱（主記憶體），然後走回流理台；再走到冰箱拿出切好的菜，放進鍋子炒，炒完又放回冰箱；最後再從冰箱拿出來裝盤。這樣來回跑冰箱（讀寫記憶體）非常浪費時間。
- **算子融合後**：你把切菜板、鍋子和盤子都放在手邊（晶片內的 SRAM 或暫存器）。切完菜直接下鍋炒，炒完直接裝盤，一次氣呵成。這就是算子融合，它極大地省去了不必要的搬運時間，讓整體計算速度大幅提升。

## 什麼是算子融合？ (深入解析)
在深度學習框架（如 PyTorch、TensorFlow）中，模型通常被表示為一個計算圖（Computational Graph），由多個獨立的算子（Operator）組成，例如矩陣乘法（MatMul）、卷積（Conv）、啟動函數（ReLU）等。
傳統執行方式是逐一呼叫 GPU/NPU 上的 Kernel 來執行每個算子。這會導致以下問題：
1. **頻繁的記憶體讀寫**：前一個算子的輸出必須寫回主記憶體（如 HBM），下一個算子再從主記憶體讀取出來。
2. **Kernel Launch 開銷**：CPU 呼叫 GPU 執行的次數過多，導致同步延遲。

**算子融合** 就是在編譯階段，將計算圖中相鄰的、可以合併的算子融合成一個單一的超級 Kernel。例如將 `Conv -> BatchNorm -> ReLU` 融合成一個 Kernel。資料在晶片內的暫存器（Registers）或 SRAM 中直接傳遞，無需寫回外部記憶體。

## 算子融合的分類
1. **Element-wise 融合**: 例如 `Add + ReLU`。這類融合最為簡單且效果顯著，因為 element-wise 運算極度受限於記憶體頻寬。
2. **MatMul/Conv + Element-wise 融合**: 將運算密集的矩陣乘法與後續的啟動函數融合，避免寫回龐大的中間張量。
3. **Pattern-based 融合**: 基於預定義的規則匹配（例如 [[FlashAttention3與極低精度量化硬體需求]] 中的 Attention 機制融合）。

## 實現工具與框架
現代 AI 編譯器深度依賴算子融合技術：
- **XLA (Accelerated Linear Algebra)**: Google 開發的編譯器，為 TPU 與 GPU 提供強大的融合能力。詳見 [[XLA]]。
- **TVM / MLIR**: 開源編譯器框架，提供更靈活的跨硬體融合策略。詳見 [[TVM]], [[MLIR]]。
- **Triton**: OpenAI 提出的語言，讓開發者能以 Python 語法撰寫出高效融合的自訂算子。詳見 [[Triton]]。

## 方案與研究方向 (虛擬團隊提出)

### 方案一：基於規則的靜態圖融合 (Rule-based Static Fusion)
由編譯器開發者人工撰寫常見的融合規則（Pattern Matching），在編譯階段靜態替換。
- **優點**：實作相對直觀，對於經典模型（如 ResNet, BERT）效果穩定且快速。
- **缺點**：無法應對日益創新的自定義網路結構，維護這些硬編碼規則的成本越來越高。
- **成本與維護性**：初期開發成本低，但長期維護與適應新模型的成本極高。
- **風險**：面對新的算子組合時，可能完全無法發揮硬體效能。

### 方案二：基於機器的動態搜尋 (Auto-Tuning / ML-based Search)
使用機器學習模型或啟發式搜尋演算法，自動在龐大的搜尋空間中尋找最佳的融合策略（例如 TVM 的 AutoTVM/Ansor）。
- **優點**：能夠自動適應未知的網路結構與全新的硬體後端，達到最佳或接近最佳的效能。
- **缺點**：編譯時間（Tuning Time）可能長達數小時甚至數天，對頻繁迭代的模型不友善。
- **成本與維護性**：需要大量的算力來進行編譯前的搜尋，但一旦找到最佳解，長期執行成本極低。
- **風險**：搜尋過程可能陷入局部最佳解，或者因為搜尋空間過大導致 Timeout。

### 方案三：Just-In-Time (JIT) 動態融合與 Kernel 生成
在程式執行期（Runtime），根據實際輸入的 Tensor 形狀與硬體狀態，動態生成融合的 Kernel（如 PyTorch Inductor 或 OpenAI Triton）。
- **優點**：結合了高度的靈活性，對於動態形狀（Dynamic Shapes）的模型支持度極佳。
- **缺點**：會在第一次執行時產生較高的延遲（JIT Compilation Overhead）。
- **成本與維護性**：依賴強大的現代編譯器基礎設施，技術門檻較高，但對於終端使用者來說體驗最好。
- **風險**：JIT 編譯失敗或生成的 Kernel 存在邊界條件（Edge Cases）錯誤時，難以除錯。

## 挑戰與限制
- **硬體暫存器限制**: 融合過多算子會導致每個執行緒需要的暫存器數量暴增，引發 Register Spilling（被迫將資料存到較慢的記憶體中），反而降低效能。
- **實作複雜度**: 自動探索最佳的融合策略是一個 NP-hard 問題，編譯器需要強大的成本模型（Cost Model）來決定是否要融合。
